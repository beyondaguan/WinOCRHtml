# 技术.md — WinOCR（Rust + Slint）技术文档

> 版本：v0.9.x-dev · 2026-09-27
> **维护约定**：与 `架构.md` 配对；踩坑即记（每条含现象→根因→修法），Phase 收尾验证回补。

## 1. 技术栈（含选型理由）

| 项 | 选型 | 理由 |
|---|---|---|
| 语言 | Rust 1.98.1（stable-x86_64-pc-windows-msvc） | 性能 + 单文件绿色分发；MSVC 是 Windows 一等公民 |
| UI | Slint 1.18.1（backend-winit + **renderer-software**） | 原生渲染、无 WebView；**软件渲染因本机 OpenGL 上下文创建失败**（真实机器复现），软件渲染零 GPU 依赖且本 UI 足够 |
| Win32 | windows-sys 0.59（按需 feature） | 裸绑定、签名可预测（`windows` crate 的 Result 包装在消息循环场景反而繁琐） |
| WinRT | windows 0.58（Foundation/Globalization/Graphics_Imaging/Media_Ocr/Storage(_Streams)/Win32_System_Com） | 系统 OCR（Windows.Media.Ocr）；与 windows-sys 同项目共存无冲突 |
| 图像 | image 0.25（仅 png feature） | 截图 PNG 编码；裁掉 jpeg 等减体积 |
| OCR 推理 | ort 2.0-rc.13（load-dynamic）+ ndarray 0.17 | PP-OCRv6 det/rec ONNX（**模型取自 RapidOCR 档的 PP-OCR ONNX；RapidOCR 非独立引擎、只是 PP-OCR 的 ONNX Runtime 搬运封装**）；load-dynamic 运行时加载 assets/onnxruntime.dll（ORT_DYLIB_PATH），不参与链接、免版本锁死 |
| OCR 兜底 | Windows.Media.Ocr（windows 0.58 WinRT） | 零模型体积；中文质量弱（假名混淆），仅作 PP-OCR 失败兜底 |
| 异步 | tokio 1.x（full） | 后续 OCR/翻译网络路径用；UI 线程不依赖它 |
| 基础 | anyhow / serde / serde_json / log / env_logger | 标准组合 |
| 构建 | VS Build Tools 2022（cl.exe 14.44 + Win SDK 10.0.26100） | rustc 自动定位 link.exe，**无需 vcvarsall** |
| 打包（计划） | 绿色 zip | 小工具定位、零安装 |

## 2. 工具链与构建

```powershell
rustup show active-toolchain   # 应为 stable-x86_64-pc-windows-msvc (default)
cargo build -p winocr          # 冷编译 3-20 分钟（Slint 首次），增量秒级
.\target\debug\winocr.exe
```
- 一键：双击根目录 `build.bat`（菜单：debug构建+运行 / 仅构建 / release+运行 / 退出）
- `build.bat` 的唯一真源是 `tools/_gen_build_bat.py`（**纯 ASCII + CRLF** 铁律，改脚本重新生成，勿直接改 .bat）
- registry 走 rsproxy 镜像
- 详细逐步命令见 `app/README.md`「手动构建（逐步命令）」

## 3. Slint 关键技术点

### 3.1 布局铁律（血的教训，违背必出怪相）

| # | 铁律 | 后果（实测） |
|---|---|---|
| 1 | **互斥视图用 `if 条件元素`，禁用 `visible:false`** | Slint 布局中隐藏元素**不释放空间**（≠HTML display:none）——AI 视图隐藏后仍占半屏，双栏被挤到下半屏 |
| 2 | **布局内子元素一律显式宽高** | 无高度的子元素被拉伸到布局尺寸：ComboBox 拉到 50px、999px 圆角的状态胶囊拉成正圆 |
| 3 | **整行禁用 `alignment: center`** | 全部元素作为一组居中，相对位置漂移、右侧溢出；用「左组 + 显式 spacer + 右组」 |

### 3.2 其他要点

- **渐变**：`property <brush> accent-grad: @linear-gradient(135deg, #6366f0 0%, #a5b4fc 100%);`
  用于 `background:`（color 可自动当 brush；三元表达式 `cond ? grad : surface` 类型为 brush，合法）
- **宏与生成 API**：`slint::include_modules!()` 引入组件；`callback x()` → `invoke_x()`；
  `in-out property <string> s` → `set_s(SharedString) / get_s()`；`window.as_weak()` 供跨线程
- **条件元素语法**：`if root.ai-mode : VerticalLayout { ... }`（在布局内合法，实例化才占空间）
- **设计令牌**：全部收在 MainWindow 顶部 `property <color>`（浅色 Indigo/Slate，
  权威来源 `docs/GUI设计文档.md` §3.1；用户明确不要暗色）
- std-widgets（ComboBox/TextEdit/ScrollView）为 Fluent 风格，浅色下观感正常

## 4. Win32 集成技术点

### 4.1 线程模型（详见 架构.md §5.2）

- **RegisterHotKey 必须与 GetMessage 同线程**（热键绑定线程消息队列）→ 热键服务内部
  spawn 专用线程：注册 → `GetMessageW` 循环 → WM_HOTKEY(wParam=id) → 回调
- 注册结果用 mpsc channel 回传（`recv_timeout(3s)`），调用方立刻知道成败
- 回调发生在热键线程 → 必须 `slint::invoke_from_event_loop` 投递回 UI
- 蒙版窗同理：Win32 窗口 + 消息循环跑在独立线程，结束把结果放 `static Mutex`

### 4.2 框选蒙版（services/capture.rs）

- **冻结背景**：窗口显示**前**先 `BitBlt 屏幕DC → 内存DC`，窗体自绘该背景
  （非 LAYERED 透明窗——拍到蒙版自身的问题被"先抓后显"规避）
- 窗体：`WS_POPUP | WS_VISIBLE` + `WS_EX_TOPMOST | WS_EX_TOOLWINDOW`，尺寸 = 主屏物理像素
  （winit 已设 per-monitor DPI aware，GetSystemMetrics 返回物理像素）
- 绘制（WM_PAINT）：`BitBlt 背景 → 选区外 50% 抖动压暗（CreateBitmap(2,2,1,1,[AA,55,AA,55]) +
  CreatePatternBrush + FillRect 四外围矩形）→ CreatePen(2, 品牌色) 空心边框 → DrawTextW 尺寸`
- 交互：LBUTTONDOWN 起点 / MOUSEMOVE 更新+InvalidateRect / LBUTTONUP 定稿 /
  WM_KEYDOWN VK_ESCAPE(0x1B) 取消；选区 <4px 视为误点
- 防重入：`CAPTURE_BUSY: AtomicBool`（连按 Alt+Q 不叠蒙版）
- **裸指针静态存储**：`static Mutex<Option<..>>` 要求 Sync，`*mut c_void` 不是 Send
  → DC 句柄在 static 里**存 isize**，用时 cast 回

### 4.3 GDI 抓屏

- `GetDC(null) → CreateCompatibleDC/Bitmap → SelectObject → BitBlt(SRCCOPY) → GetDIBits`
  24bpp（`biHeight = -h` 顶行在前）→ **去行对齐 padding** → image::RgbImage → PNG
- DXGI Desktop Duplication（rust-reference 有）后置：质量更高但 COM/D3D 复杂；GDI 全兼容（含 RDP）

## 5. 踩坑记录（现象 → 根因 → 修法）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 蒙版窗编译报 `no DrawTextW in WindowsAndMessaging` | windows-sys 把 DrawTextW/**EndPaint** 归在 **Gdi** 模块 | 从 Gdi 导入 |
| 2 | `UpdateWindow` 同样找不到 | windows-sys 0.59 该模块无此函数 | 删调用，`InvalidateRect` 足够 |
| 3 | `*mut c_void cannot be sent between threads`（static） | 裸指针非 Send，Mutex<Option<..>> 需 Sync | 句柄存 `isize`，使用时 cast |
| 4 | `BITMAPINFO::default()` 不存在 | windows-sys 结构体未实现 Default | `std::mem::zeroed()` + 逐字段构造 |
| 5 | `SetBkMode` 期望 i32 实收 u32 | windows-sys 常量类型不一 | `TRANSPARENT as i32` |
| 6 | `WM_DESTROY` 被当绑定变量 + `_` 臂不可达 | match 常量**漏导入** → 大写名成了绑定模式 | 补导入（此坑报错信息有误导性） |
| 7 | Slint `visible:false` 不释放布局空间 | Slint 语义 ≠ HTML | 用 `if 条件元素` |
| 8 | 状态胶囊被拉成正圆 / ComboBox 巨大 | 布局拉伸无显式高度的子元素 | 全部显式宽高 |
| 9 | 运行报 `Cannot create OpenGL context` | 本机 OpenGL 上下文创建失败（非 headless 特有） | 弃 femtovg，改 `renderer-software` |
| 10 | `cargo build` 报 `.cargo-build-lock`/`.fingerprint` 拒绝访问 | target/ 被沙箱进程留下损坏 ACL | **整删 target/ 重建**（Python shutil.rmtree 带 onerror） |
| 11 | Git Bash 设 `CARGO_TARGET_DIR=/d/...` 报 `d:/d/...` | POSIX 路径被拼接 | 必须写 Windows 原生路径 `D:\...` |
| 12 | 服务日志全看不到 | env_logger 默认 error 级 | `Builder::from_env(Env::default().default_filter_or("info"))` |
| 13 | 编译 .bat 时 `no UpdateWindow in module` 之外的怪报 | cmd.exe 路径转换/安全策略 | 见 MEMORY.md（Bash↔cmd 隔离） |
| 14 | `.bat` 中文乱码（历史教训） | cmd 按 936 解码 UTF-8 | .bat 一律**纯 ASCII + CRLF**，由 Python 真源生成 |
| 15 | 第二次截图报 `RegisterClassW failed` | 窗口类进程内只注册一次，重复注册返回 0 + 错误 1410 | `GetLastError()==1410`（ERROR_CLASS_ALREADY_EXISTS）时视为成功复用 |
| 16 | 框选蒙版**条纹花屏**（选区外条纹、选区内正常）+ 弹出瞬间闪烁 | ① 1bpp 抖动压暗刷在设备像素上就是横条纹 ② 窗口带 WS_VISIBLE 先显示、首帧 WM_PAINT 后到 ③ 背景/压暗/边框多步 GDI 逐次上屏 | ① 弃抖动刷，改 AlphaBlend 常量 alpha（全屏黑 DC，SourceConstantAlpha≈90）平滑压暗 ② 显示前预绘制首帧 ③ 背景+覆盖层先合成到 frame_dc，最后一性 BitBlt 上屏（零撕裂）+ WS_EX_COMPOSITED |
| 17 | `OcrResult.Lines()`/`AvailableRecognizerLanguages()` 方法"不存在" | windows crate **按返回类型做 feature 门控**：返回 `IVectorView` 的方法需 `Foundation_Collections` feature；构造函数叫 `CreateLanguage` 而非 `Create` | 补 feature；构造函数名以编译器建议/源码为准（crate 源就在本机 .cargo/registry，直接 grep 验证） |
| 18 | 识别耗时达算力硬下限（典型图 0.8s、密集图 3.6s），单会话整批 `run` 仍占满单核 | `ort::Session` **不可 `Clone`** 且 `run` 需 `&mut self`；并行只能省 ORT 调度开销、省不掉算力 | 识别**并行池**：`init_sessions` 建 N 个独立 rec 会话（各 `intra_threads=1`），每次识别 `mem::take` 整池 + 切块按 worker 顺序分片，`std::thread::spawn` 每片一会话并发 `run`，结束归还复用；`n_workers=min(池大小, 切块数)` 防小图丢会话 |
| 19 | Argos 直接进主工程报 LNK2038（MT vs MD） | ct2rs/sentencepiece/CTranslate2 内部混用静态/动态 CRT，须统一 `+crt-static`；全局加会翻主工程 /MD→/MT（你标过风险的全局 CRT 影响） | 改**旁路子进程**：`argos-bridge/` 独立 `[workspace]` + 自带 `.cargo/config.toml` 只对自己加 `+crt-static`，编成 /MT 自洽的 `winocr-argos.exe`；主工程零 CRT 变更、零新重依赖（详见 §4.6） |
| 20 | 编译报找不到 `CF_UNICODETEXT`（或常量类型不匹配） | windows-sys 把剪贴板格式常量归在 **`Win32::System::Ole`**（不是 `Win32::System::DataExchange`）；且 `CF_UNICODETEXT` 的类型是 `CLIPBOARD_FORMAT = u16`，而 `GetClipboardData` / `SetClipboardData` 的形参是 `u32` | 补 feature `Win32_System_Ole`；调用处统一 `CF_UNICODETEXT as u32`（P3-3 划词剪贴板路径） |
| 21 | 编译报找不到 `GlobalFree` | 同 crate 但**不同模块**：`GlobalFree` 实际在 **`Win32::Foundation`**；`Win32::System::Memory` 只有 `GlobalAlloc` / `GlobalLock` / `GlobalUnlock` / `GlobalReAlloc` / `GlobalSize` | 从 `Win32::Foundation` 导入（别在 Memory 里找） |
| 22 | `GetWindowLongPtrW` / `SetWindowLongPtrW` 在某些 target 报"不存在" | windows-sys 0.59 给这两个函数加了 `#[cfg(any(target_arch="x86_64","aarch64","arm64ec"))]` 门控——只有 64 位才有 `*Ptr` 变体 | 本工程 x86_64 可用；**将来若出 32 位包，必须退化为 `GetWindowLongW` / `SetWindowLongW`（返回 / 传入 `i32`）** |
| 23 | 剪贴板内容损坏或进程崩溃（取词 / 复制译文之后） | `SetClipboardData` **成功后该内存所有权已移交系统**，此时再 `GlobalFree` 即双重释放 | 仅在 `SetClipboardData` 返回 null（失败）时才 `GlobalFree`；成功路径**绝不**释放 |
| 24 | 划词用一段时间后彻底失效（钩子静默消失、无任何报错） | 低级鼠标钩子（`WH_MOUSE_LL`）回调超时（系统给的时限约 1s 量级）会被 Windows **静默摘掉钩子，且多半不再恢复** | 回调内**只允许**「读坐标 + 比位移 + `try_send`（非阻塞）」；禁止 sleep / 剪贴板 / 网络 / 翻译。重活全部丢给工作线程（本工程 `winocr-selection-work`） |
| 25 | 钩子回调里取不到自定义状态（回调是 `extern "system" fn`，不能捕获闭包） | 自由函数没有 `self` / 闭包环境可依 | 状态（发送端 + 开关）放进**安装钩子那个线程**的 `thread_local!` —— `WH_MOUSE_LL` 回调必然在该线程执行（经其消息队列派发），从而避免全局可变 static |
| 26 | `SendInput` 构造 `INPUT` 数组时不知 union 字段名 | windows-sys 的结构是 `INPUT { r#type, Anonymous: INPUT_0 }`，按键信息在 `INPUT_0.ki: KEYBDINPUT` | 直接写 `Anonymous: INPUT_0 { ki: KEYBDINPUT { .. } }`；union **构造**是安全代码（不需 unsafe，只有读才要）。若嫌别扭可降级用 `keybd_event` |
| 27 | 气泡越界回退在多显示器上把浮层拉回主屏 | `GetSystemMetrics(SM_CXSCREEN / SM_CYSCREEN)` 给的是**主屏**尺寸，不是虚拟屏尺寸 | v1.0.0 **有意**只用它做右下越界回退（本机单屏为主，不值得为它扩大 API 面）；精确回退需 `SM_XVIRTUALSCREEN` / `SM_YVIRTUALSCREEN` / `SM_CXVIRTUALSCREEN` / `SM_CYVIRTUALSCREEN`（注意虚拟屏原点可能为负），留待 v1.1 |
| 28 | 高 DPI 下「点击气泡外部即隐」误判（点气泡右下角被当成外部，气泡意外收起） | Slint 的 `width` / `height` 是**逻辑像素**，而鼠标钩子坐标与 `SetWindowPos` 用的是**物理像素**（125% 缩放时 360 逻辑 px = 450 物理 px） | **不要**做 `dpi_scale()` 乘法（除要新增 HiDpi feature 外，窗口未显示时也拿不到所在显示器 DPI）；改为**量窗口真实物理矩形**（`FindWindowW` → `GetWindowRect`）。尺寸与位置无关，故 place 与 rect 之间无需等待 |
| 29 | 想把前台窗口句柄带进 `invoke_from_event_loop` 闭包，编译不过 | `HWND` 即 `*mut c_void`，**不是 `Send`** | 句柄以 `isize` 作为**进程内不透明令牌**传递（同第 3 条思路）；它只应原样交回 `SetForegroundWindow`，**不可**当作可跨进程的 HWND |
| 30 | 浮层想要圆角 / 半透明 / 逐像素透明，结果整块**呈黑** | ① Windows 上 winit 给**所有** Slint 窗口默认开 `with_transparent(true)`，实现是 `DwmEnableBlurBehindWindow` + 空区域（`winit-0.30.13/src/platform_impl/windows/window.rs:1231-1247`），**既不是 `WS_EX_LAYERED` 也不是 `WS_EX_NOREDIRECTIONBITMAP`**；② 软渲染呈现链路 `softbuffer-0.4.8/src/backends/win32.rs` 用 32bpp BI_RGB DIB（`biBitCount: 32` 见 :62、`CreateDIBSection` :91）+ `BitBlt(SRCCOPY)`（:189-198），**GDI 不做 alpha 合成、第 4 字节被当 X 忽略**；③ Slint 软件渲染器在「视图有透明」时给背景填 `(0,0,0,0)`（`i-slint-renderer-software-1.18.1/draw_functions.rs:855-858` 与 :888-890，注释原文 "in case the slint view has transparency"；填充调用点 `lib.rs:674-686`） | **本工程任何浮层窗口必须整体不透明**：最外层矩形用不透明 `background:` 直角铺满（如 `bubble.slint` 的 `background: #ffffff`）。另：旧笔记里 `wants_transparent = ... 或 no_frame` 这条判据带 `#[cfg(target_os="macos")]`，在 Windows 是死代码，不要拿它推理 |

### 4.4 WinRT（系统 OCR）要点（services/ocr.rs）

- **COM 单元**：WinRT 激活需先初始化；后台线程用 `CoInitializeEx(None, COINIT_MULTITHREADED)`，
  已初始化/模式变更（RPC_E_CHANGED_MODE）忽略即可
- **方法名保持 WinRT 原样 PascalCase**：`OpenAsync / CreateAsync / GetSoftwareBitmapAsync /
  RecognizeAsync / Lines / Text / Size / GetAt`（windows crate 不改名为 snake_case）
- **阻塞等待**：`IAsyncOperation::get()`（阻塞当前线程）——只在后台线程用，UI 线程禁用
- **`Try*` 方法可空返回**：WinRT 返回 null → windows crate 映射为 `Err`，所以
  `if let Ok(e) = TryCreateFromLanguage(...)` 即可表达"创建成功"
- **流程**：PNG 路径 → `FileRandomAccessStream::OpenAsync` → `BitmapDecoder::CreateAsync` →
  `GetSoftwareBitmapAsync` → `OcrEngine::RecognizeAsync` → `OcrResult.Lines()` 按行拼接
- **引擎选择**：zh-Hans → 用户系统语言 → 逐个可用语言兜底（截图中英混合，中文引擎也能识别英文）
- **语言包依赖**：Windows OCR 需要"中文语言包"已安装（Win10/11 中文系统默认有）；
  报"未安装任何语言包"时去 设置→时间和语言→语言 添加

### 4.5 PP-OCR（主引擎）要点（services/ocr.rs，移植自 rust-reference/ocr.rs）

> **术语澄清（消除混淆）**：本项目所说的"PP-OCR 主引擎" = **PP-OCR 模型权重 + ONNX Runtime 推理**，
> 与 RapidOCR 走的是同一条技术路线，但二者**不是"两个竞争引擎"**：
> - **PP-OCR** 是**模型**（百度飞桨开源的 OCR 族：DBNet 检测 + CRNN 识别 + 方向分类），自带权重与网络结构；
> - **RapidOCR** 是**推理封装库**，本身不训练模型，只把 PP-OCR 的模型导出成 ONNX、再用 ONNX Runtime 跑（目的是摆脱 PaddlePaddle 依赖）；
> - 本项目**未引入 RapidOCR 的 Python 库**，而是用 Rust `ort` crate + 自写前后处理（DBNet 后处理 / CTC 解码 / 字典映射）**复刻了同款流程**；
> - 模型文件（`det_tiny.onnx` / `rec_tiny.onnx` / `ppocr_dict.txt`）即取自 RapidOCR / 3.4-master 的 PP-OCR ONNX 档（原名 `PP-OCRv6_det_tiny.onnx`）。
> 简言之：**PP-OCR = 模型，RapidOCR = 其 ONNX Runtime 搬运封装；本项目的引擎是"PP-OCR 模型 + ort 推理"。**

- **运行库加载**：ort load-dynamic 读 `ORT_DYLIB_PATH` 环境变量——代码内先探测
  `assets/onnxruntime.dll`（cwd/exe 目录多候选）再 `set_var`，最后 `ort::init().commit()`
- **模型目录探测**：`ppocr_dict.txt` 为锚，按 cwd/assets → exe 同级/assets 等候选查找
- **模型命名**：项目内为改名版 `det_tiny.onnx`/`rec_tiny.onnx`，同时兼容 3.4 原名
  `PP-OCRv6_det_tiny.onnx`；cls 模型未用（屏幕文字正立，无需方向分类）
- **流程**：预处理（小图 2x 放大 + 32 对齐）→ det(DBNet, NCHW ImageNet 归一化, 阈值 0.3)
  → 连通域合并(8 邻域 BFS, 过滤 <10px/细线) → 坐标映射回原图 → 框外扩 0.35·h
  → 透视裁剪(8 自由度最小二乘) → rec(高 48, CHW (-0.5)/0.5) → CTC 贪婪解码
  → score≥0.5 过滤 → y 优先排序
- **算法与 rust-reference/ocr.rs 保持同步**：改算法需双向回补
- **识别并行池（性能关键）**：`rec_sessions: Vec<ort::session::Session>` 持有 N 个独立 rec 会话
  （`init_sessions` 时各 `with_intra_threads(1)` 建 N 个，N = 逻辑核心数 clamp 2..8）；
  `recognize_cropped_fast` 把全部切块按 worker 数**顺序分片**，`std::thread::spawn` 每片持一个会话并发
  `Session::run`，结果按全局顺序拼接后做行拼接；会话用 `std::mem::take` 取走、结束后归还，避免每次 OCR
  重载模型。`ort::Session` 不可 `Clone`，不能 clone 会话，必须 **one-session-per-thread**（ort 官方推荐做法）。
  池规模稳定：`n_workers=min(池大小, 切块数)`，未配对的会话原样归还，池不被逐步耗尽。

### 4.6 Argos 离线翻译（旁路子进程，services/translate.rs + argos-bridge/）

- **动机**：ct2rs/CTranslate2 必须把编译单元统一为 `/MT`（`+crt-static`），否则 LNK2038。
  直接塞进 `winocr` 会把整个二进制翻 `/MT`（全局 CRT 影响，你标过风险）→ 故用**独立
  子进程** `winocr-argos.exe` 承载 Argos，主工程零 CRT 变更、零新增重依赖。
- **工程位置**：`argos-bridge/`（独立 `[workspace]`，不被主 workspace 包含）；其
  `.cargo/config.toml` 设 `rustflags=["-C","target-feature=+crt-static"]` + `CMAKE_GENERATOR=Ninja`
  （Ninja 绕过 MSBuild 被安全策略当 LOLBin 崩溃的 Access violation）。
- **通信**：常驻子进程，stdin/stdout **行协议**（每行一个 JSON）。
  - 请求 `{"id":u64,"text":String,"from":String,"to":String}`；响应 `{"id":u64,"ok":bool,"text":String,"score":f32,"error":String}`。
  - from/to 用语言码 `en`/`zh`/`auto`；不支持方向（ja/ko）返回 `ok:false`，主工程走在线回退链。
  - 收到 `"EXIT"` 或 stdin EOF → 子进程干净退出（winocr 关闭时 `ArgosBridge` 的 `Drop` 发 `kill`）。
- **模型加载**：`assets/argos_packages/translate-{en_zh|zh_en}-1_9`，各 82MB；首次翻译按方向
  懒加载并缓存（`Mutex<HashMap>`），模型只进内存一次、多请求复用。
- **后处理**：sentencepiece `▁` → 空格，折叠多余空格、去首尾空白（`detok`）。
- **降级**：子进程 exe 缺失/崩溃 → `ArgosBridge::request` 返回 `Err` → `Translate::translate`
  的 `"argos"` 分支自动走 `ollama → mymemory → sf` 回退链，不阻塞主流程。
- **路径解析**：exe 经 `WINOCR_ARGOS_BIN` → exe 同级 `winocr-argos.exe` → PATH；
  assets 经 `WINOCR_ASSETS_DIR` → 否则从 exe 目录**向上逐级回退（最多 4 级）**查找 `assets/`
  （已实测：exe 在 `target/release/` 可自动定位仓库根 `assets/`）。发布时把 `winocr-argos.exe`
  与 `assets/` 一并放到 exe 同级即可。

### 4.7 GUI 翻译接线（ui/mod.rs + main_window.slint）

- **触发链路**：`on_capture`（截图按钮 / Alt+Q 热键）→ 截图 → 系统 OCR 填 `ocr-src`
  → **自动翻译**填 `ocr-out`。翻译在后台线程用常驻 `tokio::Runtime` 的 `block_on` 驱动
  `Translate`（Argos 内部 `spawn_blocking` 需 runtime），不阻塞 UI 事件循环；译文经
  `invoke_from_event_loop` 回填，状态条显示「翻译完成 · N 字符 · 引擎 X」。
- **语言对 ComboBox**：顶栏 `lang-from-index` / `lang-to-index`（model 不对称：from 无「简体中文」、
  to 无「自动检测」）。`resolve_langs(idx, idx)` 把索引映射为 `Lang`，且 `from=Auto` 时按目标语言归一
  （to=Zh→from=En；to=En→from=Zh），让 Argos(en↔zh) 离线引擎命中；Ja/Ko 等其它方向走在线回退链。
- **swap-lang（⇄）**：从 stub 改为语义交换——新 from=旧 to、新 to=旧 from，并 `lang_to_from_idx` /
  `lang_to_to_idx` 映射回各自 model 的合法 index（不对称 model 退化为最近合法项）。
- **常驻实例**：`run()` 内 `Arc<Translate>` + `Arc<Runtime>`，跨 `on_capture` 等回调共享；
  `Translate::new()` 惰性启动 Argos 子进程（首次翻译时拉起 `winocr-argos.exe`）。
- **失败处理**：Argos 子进程缺失/崩溃 → `Translate` 返回 Err → 自动降级 `ollama → mymemory → sf`
  回退链，状态条提示「翻译失败: …」；不阻塞 OCR 原文展示。

### 4.7 DPAPI 密钥加密（core/dpapi.rs + core/config.rs，P2-2 落地）

- **问题**：API Key（sf_key / ai_sf_key / youdao_app_key / youdao_app_secret）明文落盘，任何能读 `%APPDATA%\WinOCR\config.json` 的人都能窃取。
- **方案**：Windows DPAPI（`CryptProtectData`/`CryptUnprotectData`），绑定到当前 Windows 用户账户。
- **实现**：`app/src/core/dpapi.rs` 通过 `libloading` 动态加载 `crypt32.dll`（不引入新 feature），base64 编码加密 blob。
- **两条序列化路径**：
  - 内存/设置页：明文字段（`sf_key` / `ai_sf_key` / `youdao_app_key` / `youdao_app_secret`），供 services 层直接使用
  - 磁盘 save()：加密为 `*_enc` 字段（`sf_key_enc` / `ai_sf_key_enc` / `youdao_app_key_enc` / `youdao_app_secret_enc`），明文字段置空后序列化
- **加载解密**：`Config::load()` 先反序列化，再调用 `decrypt_secrets(&raw_json)` 从 `*_enc` 解密到明文字段；旧版无 `*_enc` 时回退明文字段
- **自动迁移**：若加载时发现「有明文 + 无加密字段」，自动调用 `save()` 触发加密落盘，下次启动即为加密态
- **依赖**：`libloading` 0.8（已用于截图外？）+ `base64` 0.22，仅 Windows 路径启用
- **空字符串**：空密钥不加密（直接存 `None`），解密时也直接返回空

## 9. 主程序 × 扩展程序 交联 BUG 清单

> 2026-09-30 基于源码全文 + 设计文档交叉审查，对标 Manggo/Pot/Snow Shot

### 9.1 高优（功能阻断或数据错误）

| # | 问题 | 根因 | 触发场景 | 后果 |
|---|---|---|---|---|
| **X1** | **配置双向不同步** | `syncSettings`（`background.js`）仅扩展→宿主单向推送，宿主侧 `winocr_config.json` 变更不反写扩展 | 用户在宿主内改了翻译引擎为 Argos，扩展仍用 SiliconFlow | 翻译结果不一致、用户困惑 |
| **X2** | **剪贴板竞争窗口** | 宿主 `attach.rs` 线程 B 做「保存→清空哨兵→Ctrl+C→读回→还原」；扩展 `content.js` 通过 `background.js` 同样操作剪贴板做翻译/截图 | 宿主取词气泡弹出瞬间用户触发扩展翻译 | 双方读到对方的哨兵/空值，译文变成乱码或空字符串 |
| **X3** | **`CAPTURE_BUSY` 永久锁定** | `capture.rs` `static CAPTURE_BUSY: AtomicBool`，线程 panic 后不重置 | 截图线程崩溃（如 OOM） | 后续所有截图被静默忽略，用户以为坏掉但无任何提示 |
| **X4** | **`inline` 模式 `extractContents()` 破坏原 DOM 事件** | `content.js` `inline` 实现用 `range.extractContents()` 替换节点，destroy 原 DOM 引用 | 用户在含 JS 交互的页面（如 Gmail、Notion）启用整页翻译 | 原页面按钮点击失效、输入框无法聚焦、无限循环翻译 |
